Why Intune BitLocker recovery keys go missing (and how to fix it)

By Avinash Sahu · 13 November 2026 · 7 min read

You enrolled the laptops in Intune and set a BitLocker policy. Then you open a device and find no recovery key, or the laptop is not encrypted at all. If that person is ever locked out, there is no way back in. This is how I find the cause and fix it.

First: where should the key be?

For a device that is joined to Microsoft Entra ID, the recovery key should be stored on the device record in Intune and in Microsoft Entra ID. Open the device and look for its recovery keys. If there is none, work through the causes below.

The five usual causes

1. The device does not meet the requirements for silent encryption

Microsoft lists the prerequisites for silent BitLocker encryption: a TPM, native UEFI mode, Secure Boot enabled, and Windows Recovery Environment (WinRE) available. If Secure Boot is switched off in the laptop firmware, silent encryption does not happen. This is the first thing I check on a stubborn laptop, and fixing it needs someone at the device (or on a call).

2. The policy does not require the key to be stored first

In the Intune BitLocker profile, Microsoft documents these two settings together:

  • Save BitLocker recovery information to Microsoft Entra ID = Enabled
  • Store recovery information in Microsoft Entra ID before enabling BitLocker = Required

The second setting makes BitLocker wait until the key is safely stored, so you never end up with an encrypted laptop and no key.

3. The device was already encrypted before the policy arrived

If BitLocker was already on, the key may never have been uploaded. The fix is to rotate the key, which creates a new one and stores it (see the fix below).

4. The signed-in user is a standard user

Encryption can wait for a prompt if the person is not an administrator and the policy does not allow standard users to encrypt. Microsoft documents the AllowStandardUserEncryption setting for this case.

5. Two policies are fighting

A second BitLocker profile, or an old Group Policy, can conflict. In Intune, open the profile's device status and look for conflicts or errors on the affected device.

Check status across all devices

Intune has an encryption report (Microsoft's page is called "Monitor device encryption with Intune"). It lists each device's encryption readiness, encryption status and TPM version, which usually points straight at the cause.

Fix a device that is already encrypted

  1. In the Intune admin center go to Devices, All devices, and select the device.
  2. Choose the BitLocker key rotation remote action (use the ellipsis menu if you do not see it).
  3. After the device checks in, confirm a new recovery key appears on the device record.

To keep keys fresh, Microsoft also provides the Configure Recovery Password Rotation setting for automatic rotation. After a rotation the old key stops working, so note the date.

If you only need to push the existing key to Entra ID from the device, run this in an elevated PowerShell on that laptop. Test on one device first:

$id = (Get-BitLockerVolume -MountPoint "C:").KeyProtector |
      Where-Object KeyProtectorType -eq "RecoveryPassword" |
      Select-Object -First 1 -ExpandProperty KeyProtectorId
BackupToAAD-BitLockerKeyProtector -MountPoint "C:" -KeyProtectorId $id

Who can read the keys?

Recovery keys are sensitive. Limit the roles that can read them to the few people who handle lockouts, and keep a note of who they are.

From my own work

On a rollout of six Windows laptops and an iPad, I configured BitLocker so it waits until the key is stored. Two laptops stayed unencrypted with no key. The likely cause was Secure Boot turned off in the firmware, so those needed someone at the device on a call. Setting the policy to require the key first meant none of the other laptops ended up encrypted without a recoverable key.
